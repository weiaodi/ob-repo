## PwR-NL2DSL是什么框架

PwR-NL2DSL并不是一个常见的已知框架。不过，根据相关信息可以推测其可能与Programming with Representations（PwR）和NL2DSL（自然语言到领域特定语言）技术相关。

PwR是微软提出的一种软件开发方法，它依赖于由特定领域的开发人员定义的领域特定语言（DSL）。PwR使用大语言模型（LLMs）来解释用户的自然语言对话，并将其转换为DSL程序，然后再将DSL程序转换为可执行代码。

NL2DSL则是一种将自然语言转换为领域专用语言的技术，与NL2SQL（自然语言到SQL）不同，NL2DSL会先生成受限的DSL（如JSON/EBNF等），再将其编译为SQL或其他形式，它具有可跨库/跨引擎复用、正确性与安全性高、可维护性强等优势。

因此，PwR-NL2DSL可能是一种结合了PwR方法和NL2DSL技术的框架，用于通过自然语言来生成领域特定语言程序，进而实现软件开发或数据查询等功能，但目前并没有明确的关于“PwR-NL2DSL”的具体定义和详细介绍。

## rpa是什么

**RPA = Robotic Process Automation**
**中文：机器人流程自动化**

### 一、简单理解

**不是物理机器人，是“软件机器人”**：

- 一段**模拟人操作电脑**的程序
- 自动做：**点击、输入、复制粘贴、打开软件、数据搬运、报表、发邮件**等
- 适合：**重复、规则明确、量大、枯燥**的电脑工作

### 二、核心特点

- **非侵入**：不用改原有系统（ERP、CRM、旧系统），直接在界面上“模拟人”
- **规则驱动**：必须有固定流程（如“Excel→网页→填单→保存”）
- **7×24小时**、**快、准、不出错、不疲劳**
- **低代码/无代码**：业务人员也能简单配置

### 三、常见应用场景

- **财务**：发票、报销、对账、报税、银行流水处理
- **HR**：入职/离职、简历筛选、考勤统计、发Offer
- **运营**：数据录入、跨系统同步、报表生成、客服消息自动回复
- **IT**：账号开通、日志检查、批量操作

### 四、RPA vs AI

- **RPA**：**按规则执行**，不会思考、不会学习
- **AI（智能RPA）**：可识别图片、理解文本、做判断（OCR、NLP）

一句话：**RPA = 电脑上的自动化“搬运工/打字员”，帮你省时间、少出错。**

## 目前有除了cloud code之外的harness工程吗？

有的，除了 Claude Code（你说的 Cloud Code 大概率是笔误），目前已有多个成熟的 Harness 工程（Agent Harness）项目，覆盖**开源轻量、高性能、多智能体、通用框架**等不同方向。

### 一、主流开源替代（2026年热门）

#### 1. OpenHarness（港大，2026年4月）

- 定位：**Claude Code 开源平替**，1.17万行 Python（仅为 Claude Code 的 3%）。
- 核心：覆盖 Claude Code 98% 工具能力（43/44），兼容其插件生态，MIT 协议，模型无关（支持 Claude/GPT/Kimi）。
- 适用：学习二次开发、私有化部署、轻量场景。

#### 2. jcode（高性能 Rust 版）

- 定位：**极致性能 Coding Agent Harness**，Rust 从零构建。
- 优势：启动 14ms（Claude Code 3.4s），单会话内存 28MB（Claude Code 387MB），支持多会话并行。
- 适用：追求速度、低资源占用的日常开发。

#### 3. RuFlow（原 Claude-Flow，多智能体）

- 定位：**蜂巢式多 Agent 框架**（3.7w Stars），支持 60+ 智能体协作。
- 架构：Queen（战略/战术/自适应）+ Worker（研究/编码/测试等），共享记忆，支持多模型（Claude/GPT/Gemini/Ollama）。
- 适用：复杂长周期任务、团队级 AI 协作。

#### 4. OpenClaw / SemaClaw（通用个人 Agent）

- 定位：**通用个人 AI Agent Harness**，主打安全与可扩展性。
- 特性：DAG 编排、PermissionBridge 安全层、三层上下文管理，支持个人知识库构建。
- 适用：日常助理、个人知识管理、轻量自动化。

#### 5. Chorus（中国团队，AI-人协作）

- 定位：**全生命周期 Agent Harness**，TypeScript 构建，AGPLv3 协议。
- 特色：逆向对话（AI 提议、人验证）、多 Agent 角色（PM/开发/测试），强调人在回路。
- 适用：敏捷开发流程、AI 辅助团队协作。

### 二、其他值得关注

- **Hermes**：主打**自学习闭环**，强调从经验中成长，支持8种外部记忆，适合长期个性化助手。
- **Codex CLI（OpenAI）**：OpenAI 官方编程 Harness，类似 Claude Code，适配 GPT-4o 等模型。
- **LangGraph（LangChain）**：**多 Agent 编排框架**，可定制 Harness 层，适合构建复杂工作流。

## Agent在AI领域一般分为什么东西？然后通过几个技术拆分出来？

### AI Agent 核心分类 + 底层技术拆解（通俗版，无废话）

### 一、AI Agent 领域主流分类

#### 1. 按能力形态分

- **单任务Agent**：只干一件事，如文档总结、爬虫、邮件自动回复
- **多任务通用Agent**：能自主规划、多步骤完成复杂目标（如做一份调研报告、写完整项目方案）
- **专属垂直Agent**：行业定制，如客服Agent、办公OA Agent、游戏NPC Agent、代码开发Agent

#### 2. 按架构模式分

- **反射式Agent**：感知→直接行动，无复杂思考
- **规划式Agent**：先拆解目标、做任务规划，再分步执行
- **记忆型Agent**：有短期/长期记忆，能记住历史对话、任务上下文
- **工具调用Agent**：能调用外部工具（搜索、代码解释器、API、数据库）

#### 3. 按运行形态分

- **会话式Agent**：聊天框交互（日常最常见）
- **自动化工作流Agent**：后台静默跑任务，无人值守
- **多智能体（Multi-Agent）**：多个Agent分工协作（规划Agent+执行Agent+反思Agent+检索Agent）

### 二、AI Agent 核心底层技术拆分（5大核心模块）

#### 1. LLM 大模型基座

Agent的大脑，负责**理解、推理、思考、生成指令**（GPT、DeepSeek、通义千问等）

#### 2. 提示词工程 & 角色编排

CoT思维链、Few-Shot、角色设定、指令约束，让LLM具备Agent行为逻辑

#### 3. 记忆系统（Memory）

- 短时记忆：当前对话上下文
- 长时记忆：向量数据库存储历史任务、用户偏好、知识库
- 记忆召回、遗忘、更新机制

#### 4. 任务规划 & 拆解（Planning）

把大目标拆成小子任务，经典：

- 链式规划、分层规划、ReAct 框架（推理+行动）
- 自主决策下一步该做什么、调用什么工具

#### 5. 工具调用 & 行动执行（Tool Use）

对接外部能力：

- 搜索、代码执行、API接口、数据库、文件读写、浏览器浏览
- Function Calling 函数调用是核心技术

#### 6. 反思与迭代（Reflection）

执行完任务后**自我复盘、纠错、优化步骤**，越用越聪明

### 极简一句话总结

AI Agent = **大模型大脑 + 记忆 + 任务规划 + 工具调用 + 自我反思**
 分类就是：**单/多任务、通用/垂直、单Agent/多Agent**。

## SDD 配套工具很多，不强制要求，大家可以自由选择，现阶段探索为主，部分工具：

### 先说明背景：

SDD = **Spec-Driven Development 规范驱动开发**，核心思路：**先把需求、方案全部梳理完整，再让AI写代码**，避免AI理解偏差、反复返工。
 下面四个都是配合 Claude Code（VSCode里的AI编码插件）的配套流程工具，属于团队现阶段试验探索，不用强制固定某一个：

### 1、speckit（Spec Kit）

GitHub官方开源的完整SDD流程工具包。

- 特点：流程非常完整，会一步步主动追问模糊需求，自动生成**用户故事、验收标准、架构方案、任务清单**，整套文档产出极多、约束很强。
- 适合：复杂业务功能，需要严谨需求沉淀、长期可追溯的开发，但节奏偏重，生成内容量大。

### 2、claude code plan mode

Claude Code 自带的原生规划模式，不需要额外装插件。

- 特点：轻量化，开启后AI**只做方案思考、只读代码，不会直接修改文件**，先列出要改动哪些文件、几种实现方案，你确认同意之后，再开始写代码。
- 适合：中小型功能、不想搞复杂流程，只想加一层“先规划再编码”的简单约束。

### 3、openkit

AI工程化编排框架，目前团队还没有实际落地实践。

- 定位：偏向整套AI工作流托管，可以把多个AI能力串联起来，自动走「接收需求→分析→开发→自测→提交PR」一整条流水线，属于更偏向工程化落地的高阶工具。

### 4、super power（Superpowers）

Claude生态里的轻量技能插件，和speckit思路接近，但轻量化很多。

- 特点：同样是SDD需求梳理，但没有speckit那么繁琐，自定义规则、业务流程更灵活，日常迭代小功能用起来更舒服，复杂度介于plan mode 和 speckit中间。

### 简单选型总结

- 想要严谨留文档、复杂需求：用 speckit
- 追求简单省事、轻度约束：直接用 Claude 自带的 plan mode
- 日常中等复杂度迭代：super power
- openkit 暂时先观望，等有人试过再用

## ai时代把公司变成github的形式， 这个是什么？

### 一句话定义

**把公司变成GitHub形式 = Org as Code（组织即代码），AI原生组织模式**
 不再是传统金字塔层级公司，整套企业运转逻辑模仿开源仓库协作范式；所有工作、知识、流程、决策**版本化、可追溯、结构化，兼容AI Agent自动读写**。

> 通俗理解：整个公司如同一个巨大Git仓库。

### 一、GitHub模式核心特征（对照传统公司）

#### 1. 底层范式：仓库Repo代替部门

- 传统：按职能划分部门（产品部、研发、运营），自上而下派任务
- GitHub式：**项目=仓库repo**；所有文档、需求、会议纪要、方案、任务全部放进Repo
  Issue=任务需求，PR=提案/变更申请，评论=评审，Commit=修改记录

#### 2. 协作机制：PR评审替代层层审批

任何改动（需求调整、流程修改、预算方案、产品文档）走**提案→评审→合并**。
 任何人可以提交PR；重要变更公开讨论、留下永久记录；可回滚历史版本。

#### 3. 知识全部结构化、机器可读（AI时代关键）

传统企业：文档散落在飞书/微信/邮件，非结构化，AI很难抓取上下文。
 GitHub模式：统一Markdown、结构化文本，拥有完整API。
 ✅ **人类和AI Agent可以平等参与协作**：AI自动创建Issue、生成文档、提交PR、汇总周报。

#### 4. 组织弹性：流动团队，弱化固定编制

类似开源项目：人员基于Repo自发协作，没有严格上下级。
 想参与某个项目，直接进入仓库提交贡献；项目结束，团队自然解散。

#### 5. 资产可复刻：支持Fork

成熟的业务流程、组织规范可以直接Fork一份，快速孵化新项目、新业务线。
 Karpathy提出的**OrgCode**核心观点：组织运作规则可以像代码一样复制、修改、分发。

### 二、两种常见解读，不要混淆

#### 解读A（内部落地：企业内开源 Innersource）

现实大量AI创业公司正在实践：
 全员统一使用GitHub/GitLab。产研、产品、市场所有工作沉淀在仓库；需求、PR、文档打通，AI直接对接工作流。
 👉 你正在做**AI文档、多维表产品**，赛道内很多团队就是这套实践。

#### 解读B（终极构想：分布式开源式公司）

更进一步：公司边界模糊，不限于全职员工。外部开发者、兼职、AI智能体都可以提交贡献，按贡献分配收益，类似开源社区。

### 三、为什么只有AI时代才流行这套模式？

1. 传统模式下，大量事务协调依靠人，GitHub协作流程太重；
2. **AI Agent需要标准化接口、可追溯上下文**。碎片化办公工具无法喂给AI；Git仓库天然提供统一上下文、版本、事件流；
3. AI可以承担大量机械工作：自动跟进issue、文档生成、变更巡检，抵消PR流程带来的协作成本。

### 四、和你业务（AI文档/多维表）的关联

目前痛点：Notion、飞书文档、多维表**缺少原生版本变更流、PR评审机制、细粒度变更溯源**。
 GitHub式组织的需求，催生一类产品方向：

> 融合「多维表+文档 + Git版本控制 + 提案评审(PR)」一体化工作空间，面向AI Agent友好。

1. 非技术岗位上手门槛高，普通人不习惯PR、分支概念；
2. 完全去中心化容易缺乏决策效率，需要设计治理规则；
3. 权限、保密、财务、人事很难完整放进Repo，一般是混合模式，不会100%照搬开源。

## webmcp的技术实现细节

### WebMCP（Web Model Context Protocol）技术实现全细节

WebMCP 是 W3C 推动的浏览器原生标准，核心是让网页主动暴露结构化业务工具给 AI Agent，告别传统 DOM 解析、视觉点击的低效交互，Chrome 146+ 已提供原生 API 支持，整体实现分为**架构分层、双轨API、通信协议、安全机制、执行沙箱、落地适配**六大模块。

### 一、整体三层桥接架构（核心运行模型）

WebMCP 采用客户端解耦架构，不依赖后端中转，完全在浏览器本地完成能力暴露，三层职责清晰：

1. **Web应用层（Provider）**
   网页前端通过声明式HTML/JS命令式API注册工具，封装业务动作（查询订单、提交表单、数据导出），绑定DOM事件与业务逻辑，对外输出标准化JSON Schema契约。
2. **浏览器内核层（Broker）**
   原生提供 `navigator.modelContext` 全局API，负责工具注册、权限校验、调用转发、上下文隔离，是AI Agent与网页之间的安全中介，天然继承用户登录态、Cookie、页面权限。
3. **AI Agent层（Consumer）**
   MCP兼容客户端（Claude、Cursor、自定义Agent）通过标准协议发现工具、校验契约、发起调用，接收执行结果并回传给大模型做后续推理。

### 二、双轨API实现（两种接入方式）

#### 1. 声明式API（零JS侵入，存量表单快速适配）

针对传统HTML表单页面，只需在原生form标签新增自定义属性，浏览器自动解析为AI可识别工具，无需编写JS逻辑：

```html
<form toolname="order_search" tooldescription="查询用户历史订单" tool-csrf-header="X-CSRF-Token">
  <input name="order_id" type="text" description="订单编号">
  <button type="submit">查询</button>
</form>
```

- 核心属性：`toolname`（工具唯一标识）、`tooldescription`（模型可读描述）、`inputSchema` 自动从表单字段推导
- 优势：存量系统改造成本极低，兼容老项目；浏览器自动完成表单提交、CSRF校验、结果序列化

#### 2. 命令式API（动态复杂业务，JS注册工具）

面向SPA、动态交互场景，通过浏览器原生API注册自定义工具，支持异步逻辑、复杂数据处理，是主流业务的实现方式：

```javascript
// 浏览器原生注册工具
navigator.modelContext.registerTool({
  name: "export_sales_data",
  description: "导出当前页面销售统计数据，支持csv格式",
  inputSchema: {
    type: "object",
    properties: {
      dateRange: { type: "string", enum: ["7d", "30d", "90d"] },
      format: { type: "string", default: "csv" }
    },
    required: ["dateRange"]
  },
  // 执行函数：浏览器内运行，可访问页面DOM、接口、本地状态
  execute: async (params) => {
    const rawData = await fetchSalesApi(params.dateRange);
    return { data: convertToCsv(rawData), downloadUrl: URL.createObjectURL(blob) };
  }
});
```

- 执行上下文：工具函数运行在当前页面的JS上下文，可直接操作DOM、调用页面已有接口、复用业务权限，无需重复鉴权
- 类型约束：输入输出严格遵循JSON Schema，模型调用前做参数校验，避免非法入参

### 三、通信协议与调用流程

#### 1. 标准MCP通信规范

WebMCP 兼容 MCP 2.0 协议，传输层默认采用 **SSE（服务端推送）+ HTTP POST** 组合：

1. 连接建立：AI客户端发起SSE长连接，浏览器保持心跳，用于主动推送工具列表、状态变更
2. 服务发现：Agent通过 `listTools` 请求，浏览器返回当前页面所有注册工具的Schema清单
3. 工具调用：Agent构造JSON-RPC 2.0格式请求，POST发送调用参数
4. 结果返回：浏览器执行execute函数，同步/异步返回序列化结果，SSE通道推送执行状态

#### 2. 完整调用时序

1. 用户打开支持WebMCP的网页，前端执行工具注册逻辑
2. AI Agent扫描浏览器暴露的`modelContext`能力，拉取全量工具元数据
3. 大模型根据用户指令，匹配对应工具，校验参数合法性
4. 浏览器接收调用请求，完成安全校验后执行本地JS逻辑
5. 执行结果原路返回Agent，模型整理结果响应用户
6. 浏览器维护工具生命周期，页面卸载时自动注销所有注册工具

### 四、安全机制（核心设计，规避Agent滥用风险）

WebMCP 内置多层安全防护，防止恶意Agent窃取数据、越权操作：

1. **Ed25519 签名校验（X-WMCP-SIG）**
   网页返回的工具元数据携带数字签名，浏览器通过DNS绑定的公钥验签，防止工具清单被篡改，避免虚假工具注入。
2. **元素级CSRF防护**
   每个工具可独立配置CSRF校验规则，请求必须携带页面注入的`csrf_token`，在指定请求头/表单字段回传，服务端做双重提交校验，兼容老项目的CSRF逻辑。
3. **执行沙箱隔离**
   工具执行函数被浏览器沙箱限制，无法跨域访问其他页面资源，仅能操作当前页面DOM与接口；敏感数据支持JWE加密传输，PII、支付信息不会明文暴露给模型。
4. **权限粒度控制**
   工具可定义调用权限，仅允许已登录用户、指定页面上下文触发；浏览器对敏感操作（提交支付、删除数据）增加人工确认钩子，Agent无法静默执行高危动作。
5. **内部URL脱敏**
   对外暴露的工具参数仅返回符号化端点（如`@CHECKOUT_API`），真实后端地址对Agent不可见，避免接口泄露。

### 五、WMCP元数据文件（结构化交互描述）

网页可根目录放置 `page.wmcp` JSON文件，预定义页面交互图谱，AI无需解析原始HTML即可获取所有可操作元素，大幅减少模型Token消耗：

```json
{
  "elements": [
    {
      "toolId": "order_submit",
      "semanticRole": "提交订单",
      "domSelector": "#submit-btn",
      "securityPolicy": {"requireConfirm": true, "csrfHeader": "X-CSRF"},
      "workflow": ["选择商品", "填写地址", "提交订单"]
    }
  ],
  "context": {"cartStatus": "unpaid", "userLevel": "vip"}
}
```

- 作用：提前梳理DOM到业务动作的映射，Agent直接读取结构化交互图谱，替代原始HTML解析，token占用降低90%以上，响应延迟显著优化。

### 六、浏览器原生实现细节

1. **API挂载**：`navigator.modelContext` 为浏览器全局只读对象，仅在安全上下文（HTTPS/localhost）可用，HTTP环境禁用
2. **工具注册限制**：每个页面最多注册100个工具，防止页面暴露过度能力；跨iframe场景下，仅主框架可注册全局工具，子iframe工具需主框架授权
3. **Polyfill兼容**：低版本浏览器可引入WebMCP polyfill，降级为基于PostMessage的跨上下文通信，业务代码无需改动
4. **调试能力**：Chrome DevTools 新增ModelContext面板，可查看已注册工具、调用日志、Schema校验结果，支持手动模拟Agent调用调试

### 七、与传统网页Agent方案的核心差异

| 实现维度 | 传统DOM解析/视觉Agent | WebMCP方案 |
| --- | --- | --- |
| 交互方式 | 模型猜测UI、点击坐标、解析DOM树 | 网页主动暴露契约化工具，模型按Schema调用 |
| Token开销 | 单页面上万token解析成本 | 仅传输必要工具元数据，数百token |
| 稳定性 | 页面样式、DOM结构变更直接失效 | 工具契约版本化，前端兼容后上层无感知 |
| 权限安全 | Agent拥有页面全量操作权限 | 细粒度工具权限，沙箱隔离执行 |
| 接入成本 | 模型侧做大量页面适配 | 前端极低成本改造，一次接入全Agent兼容 |

### 八、落地工程化要点

1. **工具版本管理**：工具新增/迭代时升级Schema版本，Agent自动兼容新旧契约，避免调用报错
2. **错误标准化**：工具执行抛出标准化错误码（参数错误、权限不足、业务异常），模型可自主重试或提示用户
3. **上下文持久化**：网页可通过`modelContext.setContext`共享业务状态（表单草稿、购物车数据），Agent跨调用保持上下文连贯
4. **跨页面联动**：多页面工具可通过浏览器全局上下文做状态同步，支持跨页面复杂业务流程编排

## codex的cc是什么

### Codex 语境里的 CC

**CC = Claude Code（Anthropic 的终端AI编程智能体）**

### 1、codex-plugin-cc 是什么

OpenAI 官方插件 `codex-plugin-cc`

- 名字里 **cc = Claude Code**
- 作用：**在 Claude Code 内部直接调用 OpenAI Codex**
- 典型用法：

```
/codex:review        # Codex 代码评审
/codex:adversarial-review # 对抗式审查（跨模型查漏）
/codex:rescue        # 将开发任务交给 Codex 执行
```

逻辑：Claude Code 写代码，Codex 独立审核，规避**同模型思维盲区**。

### 2、区分两个容易混淆概念

1. **Codex**：OpenAI 编程Agent（GPT-5系列驱动，终端/IDE工具）
2. **CC（Claude Code）**：Anthropic 终端原生编程Agent

> 圈内聊天经常简写：
>  Codex = OpenAI Codex
>  CC = Claude Code

### 3、额外避坑

不要和下面两个CC弄混：

- CC（Creative Commons）知识共享许可证，和Codex工具无关；
- cc-switch：本地多模型切换工具，**不是 Claude Code**，只是用来统一管理Codex/CC等客户端。

### 极简总结

你在 AI 编程圈子看到「Codex + CC」，**CC 就是 Claude Code**。
