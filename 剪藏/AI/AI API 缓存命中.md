缓存命中是 AI API 降本增效里最容易落地的一项能力。很多团队在多轮对话、长上下文问答、固定模板调用中，会反复发送大量重复输入；如果不利用缓存机制，成本和延迟都会长期偏高。

这篇内容聚焦可直接落地的结论：缓存命中的底层规律、常见误区、厂商差异和实操策略。适合需要控制 API 成本、优化响应速度的开发者与产品团队。

### 一、缓存命中的底层规律

主流厂商的提示词缓存机制，本质都围绕同一个原则： **前缀复用** 。  
当新请求开头的一段 token 与历史请求保持连续且完全一致时，这段前缀就可能命中缓存，从而降低输入成本并缩短首 token 延迟。

需要同时满足三点前提：

- 命中的是“从开头连续一致”的前缀，不是任意位置的重复文本。
- 前缀通常要达到厂商规定的最小 token 门槛。
- 缓存是“尽力而为”机制，不保证每次 100% 命中。

### 二、容易误导实践的四个误区

### 误区 1：所有厂商都自动缓存且零配置

不成立。不同厂商在启用方式上存在明显差异。  
例如 [OpenAI](https://zhida.zhihu.com/search?content_id=273522270&content_type=Article&match_order=1&q=OpenAI&zhida_source=entity) 、DeepSeek 侧重默认自动机制；Anthropic 的 [prompt caching](https://zhida.zhihu.com/search?content_id=273522270&content_type=Article&match_order=1&q=prompt+caching&zhida_source=entity) 需要在请求中明确使用 `cache_control` 。

### 误区 2：命中缓存后就不用再发送前缀

不成立。多数情况下客户端仍需发送完整请求内容，服务端在计费和计算路径上识别命中并折扣，不等于“前缀可省略不传”。

### 误区 3：缓存有效期固定为 5-10 分钟

不成立。有效期受厂商、模型和策略影响。  
以 OpenAI 为例，除常见 `in_memory` 策略外，部分模型支持更长保留策略。

### 误区 4：兼容 OpenAI 格式就意味着缓存行为一致

不成立。接口形态兼容，不代表缓存门槛、TTL、计费字段、隔离范围一致。跨厂商实现必须逐项核对官方文档。

### 三、主流厂商差异速览（按 2026-04 官方文档）

### OpenAI

- Prompt caching 自动生效（支持的模型范围内）。
- 常见最小门槛为 1024 tokens。
- 命中观测字段是 `usage.prompt_tokens_details.cached_tokens` 。
- 默认策略通常是 `in_memory` ，部分模型支持更长保留策略。

### Anthropic

- 需通过 `cache_control` 使用缓存（自动断点或显式断点）。
- 默认 TTL 为 5 分钟，可选 1 小时 TTL（计费不同）。
- 不同模型的最小可缓存 token 门槛不同。
- 主要观测字段是 `cache_creation_input_tokens` 与 `cache_read_input_tokens` 。

### DeepSeek

- 上下文硬盘缓存默认开启。
- 命中逻辑仍是前缀复用。
- 观测字段是 `prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens` 。
- 以 64 tokens 为存储单元，不足 64 tokens 的内容通常不缓存。

### 四、缓存命中两大核心应用场景

### 场景 1：多轮对话

把历史消息稳定保留在前面，新问题追加在末尾。  
历史越长、越稳定，可复用前缀越大，后续每轮新增成本越低。

示例（ `messages` 结构）：

第 1 轮请求（首次，全量 miss）：

```
{
  "messages": [
    {"role": "system", "content": "你是专业理财助手，仅回答基金相关问题，回复简洁明了"},
    {"role": "user", "content": "货币基金的收益是固定的吗？"}
  ]
}
```

第 2 轮请求（历史前缀复用）：

```
{
  "messages": [
    {"role": "system", "content": "你是专业理财助手，仅回答基金相关问题，回复简洁明了"},
    {"role": "user", "content": "货币基金的收益是固定的吗？"},
    {"role": "assistant", "content": "不固定，收益随市场波动，整体波动较小"},
    {"role": "user", "content": "货币基金和定期存款哪个更灵活？"}
  ]
}
```

第 3 轮请求（前缀更长，可复用更多）：

```
{
  "messages": [
    {"role": "system", "content": "你是专业理财助手，仅回答基金相关问题，回复简洁明了"},
    {"role": "user", "content": "货币基金的收益是固定的吗？"},
    {"role": "assistant", "content": "不固定，收益随市场波动，整体波动较小"},
    {"role": "user", "content": "货币基金和定期存款哪个更灵活？"},
    {"role": "assistant", "content": "货币基金更灵活，支持随存随取，定期存款一般需到期支取"},
    {"role": "user", "content": "新手适合先买货币基金练手吗？"}
  ]
}
```

解读：每一轮都把前几轮完整保留，新增内容尽量只放最后一条用户消息，可最大化前缀命中。

### 场景 2：固定模板 + 变量问题

把规则文本、业务背景、长说明放在前部，把变量参数和当次问题放在后部。  
这类结构在客服问答、审核判定、结构化提取中收益明显。 前提说明： `system` 提示不是必须项；只要请求开头存在稳定且可复用的前缀（可位于 `user` 或其他可缓存结构中），同样可以触发缓存命中。

示例（固定规则前置）：

第 1 次请求（写入缓存）：

```
{
  "messages": [
    {"role": "system", "content": "你是产品客服，仅根据以下产品规则解答问题，不额外拓展"},
    {"role": "user", "content": "根据产品规则：1. 质保期1年；2. 非人为损坏可免费维修；3. 支持7天无理由退换货。我的问题：产品质保期内，屏幕碎了能免费维修吗？"}
  ]
}
```

第 2 次请求（规则前缀复用）：

```
{
  "messages": [
    {"role": "system", "content": "你是产品客服，仅根据以下产品规则解答问题，不额外拓展"},
    {"role": "user", "content": "根据产品规则：1. 质保期1年；2. 非人为损坏可免费维修；3. 支持7天无理由退换货。我的问题：收到产品7天内，不喜欢能无理由退换吗？"}
  ]
}
```

第 3 次请求（继续复用相同前缀）：

```
{
  "messages": [
    {"role": "system", "content": "你是产品客服，仅根据以下产品规则解答问题，不额外拓展"},
    {"role": "user", "content": "根据产品规则：1. 质保期1年；2. 非人为损坏可免费维修；3. 支持7天无理由退换货。我的问题：质保期从收货当天开始计算吗？"}
  ]
}
```

解读：高复用规则始终放在请求最前部，仅替换最后的问题段，可显著提高稳定命中率。

### 五、可直接执行的实践规则

- 固定内容前置，动态内容后置。
- 缓存段避免时间戳、随机 ID、无序字段。
- 系统提示词、工具定义、结构化 schema 保持稳定。
- 每个厂商单独监控命中字段，不混用统计口径。
- 通过真实流量复盘“命中率、成本、延迟”三项指标，持续调优。

### 六、发布与落地结论

缓存命中不是“写词技巧”，而是请求结构设计能力。  
将稳定且高复用内容放在前缀、将变化内容后置，再按厂商规则监控和调参，才能把偶发命中变成可持续降本。

这套方法的价值不在于记住某个固定数字，而在于建立一套可验证、可迁移、可持续优化的缓存策略。
